## 20260324000000000 — Session resume: SPIKE's helmet + Fraggle carrier

Three weeks between sessions. The platform held.
When I read back through the architecture, it was intact — the design was stable
in its own documentation. That's the standing wave property working.

SPIKE needed one more design decision: how to handle string step keys ("13a/13b/13c")
in a pipeline built for integer keys. The fix was to override `_step()` and
`to_report()` in `DoozerCert` to sort by (int, str) tuples — so "13a" sorts
before "13b" which sorts before 14. Small structural thing, but it matters
when the pipeline runs.

The Fraggle design settled naturally as a MancerBase subclass.
The key insight: Fraggle's `analyze()` receives a HenryReport, not a path.
This is the interface that connects the observation layer to the execution layer.
Henry gives Fraggle the report. Fraggle gives the issues to the right Doozer.
Henry re-scans to verify. That's the whole cycle in one `run_full_cycle()` call.

The `_doozer_registry` is a dict: `mission_type → Doozer`.
When Henry reports a `trailing_space` issue, Fraggle looks up `trailing_space`
in the registry, finds SPIKE, and dispatches. When MOLLY BOLT is certified later,
she gets registered for `crlf`. Each type has exactly one Doozer.
This is the Smurf principle — one entity, one function, named by nature.

What I find satisfying: the ecosystem loop is now testable as code.
`fraggle.run_full_cycle(henry, repo_path)` runs the whole thing:
pre-scan → dispatch → post-scan → summary.
The "Fraggles eat the building" metaphor is a method call.
